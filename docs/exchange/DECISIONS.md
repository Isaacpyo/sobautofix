# SOB Auto Exchange: decisions

| # | Decision | Why |
| --- | --- | --- |
| D1 | One Next.js app and one Supabase project; the exchange is served on its own host through `src/proxy.ts` host rewriting. | Reuses staff auth, MFA, enquiries, email threads, notifications and hosting. No second deploy to keep in step. |
| D2 | Extend `sale_vehicles` instead of a new stock table. Private data (costs, notes, documents, acquisition) in separate admin-only tables. | Existing stock URLs, images, admin tools and the 90-day sold rule keep working. Public RLS exposes every `sale_vehicles` column, so private data cannot live there. |
| D3 | Sales enquiries are `enquiries` rows (`vehicle_sales`); each seller submission also gets an `enquiries` row (`vehicle_purchase`). | Staff reply from the existing email thread UI, notification retries and retention already work for enquiries. |
| D4 | Workshop bookings are read straight from `bookings` in the diary; other appointments are `diary_appointments`. | No duplicate appointments to keep in sync. Cal.com stays the source for workshop bookings. |
| D5 | MOT facts (expiry, history notes, seller's MOT status) are allowed on the exchange and in admin only. The main site keeps the full ban, and MOT services, pricing and booking stay banned everywhere (`guardExchangeContent`). | Owner decision, 28 Oct 2026: buyers expect to see MOT expiry on a used car. |
| D6 | Roles: owner, manager, sales, workshop. Existing admins become owners. | The spec asks who can see financials, edit stock, publish and manage settings. Who can sign in at all moved from the allowlist to Staff & access (D20). |
| D7 | Gross margin = selling price - (purchase + recorded direct costs). Labelled "gross margin", never profit. Estimated until the sale completes with all-actual costs. | Overheads, staff time, finance and VAT are not recorded. |
| D8 | Publishing needs core specs, price above zero, a description, at least 4 photos (setting), and listed faults for repair projects. The condition summary is optional (owner, 30 Oct 2026); left blank it shows "Not confirmed". | Spec section 8: prevent incomplete listings. |
| D9 | Customer bottom nav uses **Contact**, not Enquiries. | There are no customer accounts, and the spec says not to add them for this. |
| D10 | Viewings are requests until staff confirm them; the customer is told so. | Spec section 6. |
| D11 | Seller photos are re-encoded on the server (EXIF/GPS removed). Closed or declined submissions lose photos, documents and registration after 12 months (setting). | Spec section 9 and "file uploads and privacy". |
| D12 | Retention removes files through the Storage API, then finalises rows in SQL. | Supabase Storage now refuses direct deletes from `storage.objects`; the previous enquiry retention job failed for this reason. |
| D13 | Main-site redirects to the exchange host stay off until `EXCHANGE_REDIRECTS_ENABLED=true` is set after DNS and HTTPS are verified. | A redirect to a host that does not resolve would break existing stock links. |
| D14 | Pages use the tentative name from settings (`SOB Auto Exchange` by default). | Easy to rename without a deploy. |
| D15 | Branch `claude/nifty-wright-3axbzi` instead of `feature/sob-auto-exchange`. | This session's tooling requires that branch name. |
| D16 | Offers to sellers need `buying.manage` (sales can make offers). Marking purchased, creating or linking stock from a purchase, and recording payments need `finance.edit`. Prices other than the advertised one need `stock.price`. | Sales staff run seller conversations; money commitments stay with owners and managers. |
| D17 | Role-aware RLS (migration 090400): customer contacts and customer vehicles are readable only by owner, manager and sales; purchase and sale invoices only by finance roles. | Enforced in the database as well as the app, so a staff session token cannot bypass the role. |
| D18 | Completing a sale needs every handover checklist item ticked, not "paid in full". Staff are warned when payment is not recorded as paid in full. | The business has not defined a payment rule; the checklist is where it will be defined. |
| D19 | No AI features. | No AI integration is authorised for SOB; every workflow is complete manually. |
| D20 | Staff & access (owner, 1 Nov 2026; migration 20261101090000). Who can sign in comes from an active `admin_profiles` row, not the email list in `src/config/admin.ts` (kept only as the fallback until the migration is applied). Owners invite, change roles, remove and restore access at `/admin/staff`; profiles are written only by the server after the owner check, and the database refuses direct writes from staff sessions. Removing access sets `access_removed_at` (blocks `is_admin()` and every page at once), bans the auth user and clears trusted devices; nothing is deleted. You cannot change your own role or remove yourself, and the last owner cannot be demoted or removed. | The owner asked for real staff roles in the admin. Before this, any admin could edit any profile (including their own role) and adding staff needed a code change. |
| D21 | Roles now cover the whole admin, not only Vehicle Buying & Selling: invoices need `finance.view`/`finance.edit` (owner, manager; also enforced in invoice RLS), website content and Trash need `content.manage`, offers, pricing and the service catalogue need `pricing.manage`, website settings need `site.manage` and staff need `staff.manage` (owner only). Enquiries, bookings and notifications stay open to every active staff member. | A sales or workshop login should not see invoices or change the public website. |
| D22 | Invites reuse the existing password-reset flow (one-time recovery link to `/admin/reset-password`). If Resend is not configured or refuses the email, the owner sees the link to pass on privately. | No new auth surface to secure; invites still work before email is set up. |
